Publishing workflow

The compliance gate

Thirteen checks run by tools/check_site.py after the build and before the deploy. Any failure exits non-zero, so the GitHub Actions job fails and nothing publishes. This is the "gate in front of the parts that cannot be automated" from the brief, made boring and mechanical — the parts that can be automated (link formatting, disclosure presence, register consistency) are the ones being automated.

What is deliberately not automated

  • Deciding what a product is. Listing confirmation is a human click with a date attached; intake is tools/product_intake.py.
  • Judging whether a claim is 'overbroad'. CHK-03 catches banned strings, not clever ones. That needs an editor, so the register asks for one.
  • Whether disclosure placement satisfies a regulator. We can check it exists and where; we cannot check comprehension.
  • Anything that needs Program Content. No scraper, no price cache, no review corpus, no model trained on Amazon data — that is the agreement, not our caution. [S10]

Running it yourself

python3 tools/build_site.py && python3 tools/check_site.py — add --strict-flags to make any open compliance flag a failure, and python3 tools/build_site.py --check to prove site/ matches what the tools produce. The workflow runs all three.

Deliberate design: the gate lives in the repo, not in someone's diligence, so a future session that forgets the rules is stopped by a red check instead of by an account suspension.
