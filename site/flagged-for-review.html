FLG-002 · The five submitted links use host `link.amazon` and 9-character identifiers

data open

What we found
Every submitted URL is https://link.amazon/<identifier> where <identifier> is 9 characters: B04G1MEwY, B02NbDxp3, B00hJ57DV, B0c8moW59, B0f3GKalj. Public examples of an item identifier on Amazon are 10 characters, and Amazon's own policy text refers to 'Amazon Standard Identification Numbers (ASINs)' without publishing a length definition that this session could retrieve.
What we did about it
Recorded the strings verbatim, counted them, generated a candidate /dp/ URL by mechanical substitution, and refused to describe either as valid or invalid. No product attribute was filled from the identifier.
How to close it
Paste each identifier into Amazon's search box while signed in to the enrolled account, or generate the link from SiteStripe, and record what actually resolves. Then run tools/product_intake.py confirm.
Sources
  • https://affiliate-program.amazon.com/help/operating/policies

FLG-003 · Compliance status of the supplied short links: unresolved

compliance open

What we found
Two primary clauses bear on it and neither settles it. Participation Requirements 6(w) prohibits using a link shortening service 'in a manner that makes it unclear that you are linking to an Amazon Site' - a presentation test, not a format ban. Commission Income Statement 2(e) disqualifies purchases arriving through a 'Redirecting Link' that sends users indirectly to Amazon via an intermediate site without an affirmative click there - a tracking test. Whether link.amazon is (i) an Amazon-owned short-link surface that preserves the tag, (ii) an unrelated intermediate, or (iii) nothing at all, cannot be determined without clicking it from a browser.
What we did about it
Did not claim the links are invalid, per instruction. Did not publish them as affiliate links either. They are listed as submitted inputs with the two clauses attached, and the site emits direct, properly tagged /dp/ links generated from confirmed data instead.
How to close it
One test closes it: from a signed-in session with the enrolled account, click the short link, check the final URL for tag=shopnow047c-20, and check the Associates reports for the click the following day. Record the outcome in data/products.json (observed_redirect_target) and mark this flag resolved or escalated.
Sources
  • https://affiliate-program.amazon.com/help/operating/policies

FLG-004 · The 'AI-powered agent that researches, analyses and scrapes Amazon' part of the brief collides with the licence

compliance open

What we found
The IP License prohibits using Program Content to develop or improve large-language, multimodal or machine-learning models, and prohibits accessing or using Creators API / PA API / Data Feeds 'for the purpose of aggregating, analyzing, extracting, or repurposing any Product Advertising Content' without express prior written approval. It also excludes data-mining and robot tools from the licence, bars Program Content from browser extensions and client-side software, and adds Agent Terms requiring any autonomous software touching Program Content to self-identify as 'Agent/[name]' in the User-Agent string and not to mimic human interaction.
What we did about it
Built the automation that is unambiguously inside the licence - data plumbing, validation, generation of our own editorial content from our own data files, link construction, publishing gates, reporting - and left every Amazon-facing collection step behind a written-approval gate rather than quietly implementing it. Nothing in tools/ opens a socket to amazon.com.
How to close it
Decide the intended data source for product signals (see Q-04, SG-01, SG-02). Options: (a) licensed API use with attributes displayed only from a fresh call and no analytics store, (b) written Amazon approval for analysis use, (c) our own hands-on test data only, (d) drop the automated research claim from the roadmap.
Sources
  • https://affiliate-program.amazon.com/help/operating/policies

FLG-009 · A GitHub Pages project site is a weak substrate for the ambitions in the brief

infrastructure open

What we found
Pages deployment (the workflow in T-12) publishes static files only: no server-side rendering, no POST handling, no rewrite rules, and the site lives under the /Affil3/ project path, which also means robots.txt is not at the host root where crawlers expect it.
What we did about it
Kept everything deployable on Pages (static, relative URLs, no build-time secrets, no server) and shipped the collector, scheduler and intake tools as processes you can run elsewhere. Consequences: no server-rendered pages, no form handling, no email capture endpoint, no rewrite rules, and the URL carries /Affil3/.
How to close it
Answer Q-11. If the answer is 'stay on Pages', accept the limits in writing and remove the endpoint-dependent tasks from the roadmap. If it is 'move', the only code change needed is measurement.endpoint plus the base_url in data/program.json, then rebuild.
Sources
  • https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages

FLG-010 · Two 'verification' requirements in the brief are in tension and were resolved in favour of the reader

policy resolved-by-decision

What we found
The brief asks for a page that reads like a shop and a table where every row carries an official source link. With five unresolvable identifiers, a fully sourced table is mostly empty cells, which reads like an audit and converts nobody.
What we did about it
Split the surfaces. The reader-facing pages (front page, shelf, guides, product pages) carry plain language and only verified or explicitly marked-assumed facts. The evidence lives in one Inside section - source register, decision register, questions, flags, ledger, measurement, gate - reachable from the footer and one nav group, exactly as the brief's 'publication' row asked.
How to close it
If you would rather have the tables on the product pages themselves, flip layout.product_tables_inline in data/layout.json and rebuild.
